# Guidelines

- For new DOM/browser API usage, use `app.ownerDocument` and `app.ownerWindow` instead of globals; without `app`, derive them from the mounted node's `ownerDocument` and its `defaultView`.

# Linked file assets (excalidraw-app/linkedAssets)

- Feature-gated by `VITE_APP_ENABLE_LINKED_FILES` (string compare against `"true"`); desktop Chrome/Edge only (File System Access API).
- App-layer code lives in `excalidraw-app/linkedAssets/`; the library (`packages/`) must never import from it — the library calls into the app through `packages/excalidraw/linkedAssetsBridge.ts` (`getLinkedAssetsBridge()`, null = feature disabled) and the image-cache resolver injected via `setLinkedImageResolver()` (`packages/element/src/image.ts`).
- Link metadata lives in `element.customData.linkedFile`; sync-frame folder bindings and the manifest live in `frame.customData.syncFolder`. Both survive scene save/load automatically — never store feature data in the linked folder itself.
- Linked images keep only a webp thumbnail (max side 512px) in BinaryFiles; originals are read from disk. Background reconciliation (verifier) must use `CaptureUpdateAction.NEVER` so it never pollutes undo history. `customData.linkedFile.width/height` record the original's dimensions so the render cache can map crop coordinates onto the thumbnail (missing in legacy scenes → falls back to reading the original from disk).
- Duplicating a linked image (copy/paste, duplicate action, alt-drag) clones `customData.linkedFile`; the sync engine detects clones via the manifest (`duplicate.ts`) and gives each clone its own on-disk copy with a sequence suffix (`name-1`, `name-2`…).
- Deleting a linked image on the board only hides it (native `isDeleted`); the file on disk is untouched. Real on-disk deletion happens via the sync frame's context menu "delete hidden images", which first opens a confirmation dialog listing the affected files (`linkedAssets/ui/DeleteHiddenImagesDialog.tsx`, executed by `frameActions.ts` → `deletion.ts`, interactive permission). The frame menu also has "show hidden images" and "reset layout". Deleting the sync frame itself opens a dialog (`linkedAssets/ui/OrphanedFolderDialog.tsx`) asking whether to also remove the folder's images from the board (`deleteFolderImages`); either way the link metadata is stripped (`unlinkFolderLinks`) and files on disk are never touched.
- Folder files unknown to the manifest are auto-imported into the frame in a grid (`importer.ts`); cell size matches the average of existing frame images, falling back to a share of the frame size. The frame grows downward automatically when the grid overflows it (`growFrameToFit`, never shrinks). The "reset layout" frame action reuses the same grid helpers (`gridColumns`/`gridPositionFor`/`fitImageToCell`) with fresh-import sizing, lays images out in manifest order, restores cell-fitted sizes, unhides hidden ones and pulls back images dragged out of the frame.
- Selected linked images get a small link badge inside their top-right corner, rendered on the interactive canvas (`renderLinkedImageBadge` in `packages/excalidraw/renderer/interactiveScene.ts`); a selected sync frame also outlines its linked images dragged outside the frame with a light blue dashed border (`renderLinkedOutOfFrameHighlights`). A single selected linked image shows its bound folder's name in the left properties panel (`packages/excalidraw/components/Actions.tsx`, looks up `customData.syncFolder.rootName`).
- The sync frame context menu also has "refresh from folder" (`actionRefreshSyncFrame` → `verifySyncFrame` in `verifier.ts` — same reconciliation as the background verify, but it may prompt for permission since it's a user gesture). `createSyncFrame` runs `verifyLinkedAssets` right after creating the frame so the folder's images import immediately; a create button also lives in the top-right UI (`renderTopRightUI` in `excalidraw-app/App.tsx`).
- The sidebar tab listing sync frames lives in `linkedAssets/ui/SyncFoldersPanel.tsx`, wired into `excalidraw-app/components/AppSidebar.tsx`; each entry expands to list the folder's synced files.
- New app-layer jotai atoms go in `linkedAssets/state.ts`; jotai is only imported via `excalidraw-app/app-jotai.ts`.
- App-layer file filters (folder scans, imports) must go through the asset-type registry `linkedAssets/assetTypes.ts` (`isImportableAssetFile`) — never hardcode extension lists. Video/PDF handlers are registered as `implemented: false` placeholders; flipping them on requires a real `generatePreview` plus renderer support.

# Rendering performance (Pixi compositor + thumbnail pipeline)

- The static scene has two renderers behind `VITE_APP_ENABLE_PIXI_RENDERER` (see `packages/excalidraw/renderer/pixiRuntime.ts`; also runtime-overridable via `setPixiRendererEnabled`). ON: `packages/excalidraw/renderer/pixiStaticScene.ts` (WebGL sprite compositing). OFF: the original Canvas2D `_renderStaticScene`. Export (PNG/SVG) always uses the Canvas2D/SVG path.
- The Pixi compositor only replaces the final blit: elements are still rendered by the existing Canvas2D/rough.js pipeline into per-element offscreen canvases via `generateElementWithCanvas` (`packages/element/src/renderElement.ts`), then uploaded as textures (`Texture.from(canvas)`). Never bypass the offscreen-canvas generation — that would lose rough.js/text/ink fidelity. Texture/sprite lifecycle is keyed by element id and the `elementWithCanvas` record identity; destroy textures on replacement/removal.
- A canvas can hold only one context type: when the flag is on, `App.tsx` gives `rough.canvas()` a throwaway canvas (never `this.canvas`), and StaticCanvas must skip frames while Pixi init is pending instead of touching the 2d context. Init failure (no WebGL) is the only permanent fallback to Canvas2D.
- Frame clipping uses a Pixi Graphics mask per frame container; arrow label holes use a Graphics with a `cut()` hole; frame outlines are Graphics redrawn per frame (they are never cached into offscreen canvases in the Canvas2D path either).
- The grid is baked once per (gridSize, gridStep, zoom, theme, resolution) into a small tile texture and drawn with a screen-space `TilingSprite` — panning only updates `tilePosition`, never retessellates. Keep it that way: reintroducing per-frame full-screen Graphics grid drawing is a known 5–30ms/frame regression on 4K.
- The Pixi path passes `allowZoomCacheBucketing: true` (and a per-frame `generationBudget`, 8 regenerations) to `generateElementWithCanvas`, so post-gesture canvas regeneration is rate-limited and zoom-bucketed (~12% buckets). The Canvas2D fallback and export paths must stay exact-zoom (no bucketing flag) — export quality depends on it.
- Thumbnail-first rendering: the image cache (`packages/element/src/image.ts`) asks the app-registered `setThumbnailResolver()` before decoding; cache entries carry `sourceScale` (decoded-natural / original-natural), and renderers multiply crop coordinates by `img.naturalWidth / crop.naturalWidth` (`renderElement.ts` image branch). Cropping forces the original first (`startImageCropping` → `updateImageCache({forceOriginal: true})`); `syncImageQuality` in `App.tsx` upgrades visible thumbnail-cached images to originals when zoom makes them larger than the cached tier.
- Tiered thumbnails (256/512/1024 webp) live in a dedicated IDB store (`linkedAssets/thumbnailStore.ts`, keyed by content-hash fileId, LRU cap 3000), generated by a background idle-queue (`enqueueThumbnailGeneration`). SVG/GIF are never thumbnailed.
- Forcing a static-canvas repaint from the app layer: `excalidrawAPI.refresh()` only setStates identical canvas offsets, and StaticCanvas is `React.memo`'d on canvasNonce/elementsMap/appState — with nothing changed the memo blocks the re-render and stale pixels stay on screen (this was the gray-PDF-after-refresh bug). To force a repaint without touching the scene, bump the scene nonce: `updateScene({ elements: [...getSceneElementsIncludingDeleted()], captureUpdate: CaptureUpdateAction.NEVER })` — same element objects, so wholesale-replace detection stays quiet and undo history is untouched; onChange subscribers must short-circuit on the echo.
- High-quality PNG/PDF export (context-menu actions) must pass `forceOriginalImages: true` to `exportToCanvas` so the export image cache skips the thumbnail resolver entirely (plain exports still use thumbnails); the export scale is computed from `customData.linkedFile.width / element.width` so linked images rasterize 1:1, capped only by canvas feasibility (16k side / 2^26 px). Before exporting, the bridge's `getUnavailableLinkedOriginalCount()` detects lost folder permissions and toasts instead of silently downgrading to thumbnails.

# PDF / video import (mediaImport)

- Videos are `embeddable` elements with a pseudo link `appfile:video/<fileId>` and `customData.sourceFile = { fileId, kind, name, ... }`; PDFs use the native `pdf` element (see below) but also keep their original bytes in BinaryFiles (base64, travels inside the .excalidraw file). `filterOutDeletedFiles` keeps files referenced via `customData.sourceFile.fileId` — without that branch the source is silently stripped on save. The same is true for app-layer persistence: `data/FileManager.ts` `saveFiles` and the restore paths in `App.tsx` (`loadImages` / tab-sync) must also collect `customData.sourceFile.fileId` — the upstream code only tracks image-element fileIds, which loses media sources on refresh.
- Rendering: native `pdf` elements draw themselves in the static canvas pipeline (no overlay); `renderEmbeddable` now only serves the video widget (`video/VideoEmbed.tsx`) and the legacy pdf fallback (`pdf/PdfEmbedWidget.tsx`), with `validateEmbeddable` allowing the `appfile:` prefix. The library only positions the overlay; overlays are inert until the embeddable is activated (same model as YouTube embeds).
- Drop entry: the library calls the `onDropFiles` prop before the image filter in `handleAppOnDrop`; the app dispatches by extension/MIME (pdf → `pdfImport.importPdfFile`, video → `videoImport.importVideoFile`) and returns true only when every dropped file was consumed. Separate "Import PDF…" / "Import video…" main-menu items and two toolbar buttons (via the library's `renderCustomToolbarItems` prop) call the same importers — file picking goes through `media/filePicker.ts`, which must keep the `<input>` appended to the DOM (iOS Safari ignores `click()` on detached inputs).
- PDFs are a **native `pdf` element type** (rectanguloid base, no fileId): state lives in `customData.sourceFile = { fileId, kind: "pdf", name, pageCount, currentPage }` and the original bytes in BinaryFiles. Rendering goes through the regular static pipeline — `drawElementOnCanvas` pulls the current page bitmap synchronously from the library bridge (`packages/element/src/pdfPages.ts`, `getPdfPageImage`/`pdfPageKey`, injected app-side via `setPdfPageImageGetter`) and paints a gray "PDF" + spinner-ring placeholder on a miss; the app (`excalidraw-app/pdf/pdfPageCache.ts`) serves pages from a runtime Map, then a **persistent IDB store** (`pdf/pdfPageStore.ts`, key `${fileId}:${page}`, WebP dataURLs, LRU 600) so refreshes redraw instantly, and only falls back to the dev server (`/api/pdf-open` + `/api/pdf-page`) on a miss — it also writes server fetches back to IDB. Two mechanisms start fetches: a **render-miss handler** (`setPdfPageMissHandler`, fired synchronously from `drawElementOnCanvas` on a bridge miss — never during export) and an `onChange` subscription in `App.tsx` that retries once BinaryFiles restore (refresh self-heal); failed fetches back off 30s before a render-triggered retry. Resizing is aspect-locked like images (both `shouldMaintainAspectRatio` ternaries in `components/App.tsx` include `isPdfElement`). The toolbar (`pdf/PdfToolbarHost.tsx`, mounted in App.tsx, positioned via `pdfSelectionStore`) turns pages with `newElementWith` + `CaptureUpdateAction.NEVER` (`pdf/pdfNavigation.ts`); extract/expand rasterize via `/api/pdf-page` and insert webp image columns (`pdf/pdfPages.ts` `insertPageImages`). The toolbar's HD-preview toggle sets `customData.sourceFile.hiRes` (`togglePdfHiRes`, NEVER-captured): the tier is part of the page cache key (`pdfPageKey(fileId, page, hiRes)` — SD keys stay tierless so pre-feature IDB caches keep hitting, HD keys get a `:hd` suffix), preview rasterizes at 1200/2400 px (`PREVIEW_WIDTH_SD/HD` in `pdfPageCache.ts`), and extract/expand follow the same tier at 1440/2880 px (`PdfToolbarHost.tsx`). The selection store's dedupe must compare `element.version`, NOT just object identity — `mutateElement` mutates elements IN PLACE during drags (same identity, version bumped), so identity-only dedupe froze the toolbar at the drag-start position. Scenes saved before this still contain `embeddable` pdf elements — those fall back to a minimal hint + source-download widget (`pdf/PdfEmbedWidget.tsx` via `renderEmbeddable`). Video remains an `embeddable` element.
- PDF placeholder healing (`pdf/pdfPageCache.ts`): a render miss marks the element `placeholderPending`; the flag clears ONLY when a draw actually paints the bitmap, so a lost heal repaint self-heals later instead of staying gray. `healFile` invalidates ShapeCache/elementWithCanvasCache and repaints via the nonce-bumping updateScene described in the rendering section — never `refresh()` (no-op through the StaticCanvas memo), and never heal from the onChange hydration chain (heal → onChange → ensure → heal recursed into React's max update depth; that chain must return on memory hits). `startPdfHealLoop` (1.5s timer, wired in App.tsx) is the convergence backstop: bitmap already cached → healFile directly; missing → `ensurePdfPageForFile`. The IDB page store is consulted BEFORE requiring the source PDF bytes — the page bitmap doesn't need them, and gating on BinaryFiles restore was what left pages gray after a refresh ("source file not restored yet").
- PDF rasterization endpoints (dev server only, `excalidraw-app/vitePdfPlugin.ts`): `POST /api/pdf-open` (raw bytes → `{ hash, pageCount, pages }`, source cached on disk under `os.tmpdir()/swhiteboard-pdfcache` by SHA-1) and `GET /api/pdf-page?hash&page&width` (webp q90 via the pdfjs-dist **legacy** Node build + `@napi-rs/canvas`; the loading task — not the doc — must be destroyed after use). Without the endpoint (production hosting) imports fall back to a fixed-size box and pages keep the placeholder.
- Video frame capture (`video/captureVideoFrame.ts`): full-resolution `drawImage`, timecode `HH:MM:SS` burned into the top-right of the JPEG, inserted to the right of the video element with `customData.timecode`/`sourceVideo`. Capture is only enabled while the video is paused.
- The sync-frame asset registry (`linkedAssets/assetTypes.ts`) still has pdf/video as `implemented: false` placeholders — folder-syncing media is a separate future feature.
- HEVC playback: files whose container/MIME is identifiable as HEVC (`video/hevc|hev1|hvc1|x-hevc|x-h265`, `.hevc/.h265`) are auto-transcoded on the **vite dev server** (`POST /api/transcode-video`, ffmpeg via `ffmpeg-static`, `viteTranscodePlugin.ts`) when the device can't decode HEVC (`transcode.ts`); undetectable HEVC containers (.mov) get a manual "转码后播放" button on the decode-error state. The transcoded mp4 replaces the BinaryFiles entry, so the scene stays playable everywhere. **Dev-only**: production static hosting has no such endpoint — the transcode path toasts and keeps the source.
